C++ API reference
=================

This page is generated by Doxygen and Breathe from the installed headers under
``include/ed/``. A downstream CMake project uses them through ``find_package(QED CONFIG)``
and ``QED::qed_engine``.

The layers are:

* The Python verbs are thin bindings (``python/qed/_bindings/sectors.cpp``) over the
  ``ed::sectors`` entry points.
* Those entry points split H into symmetry blocks.
* ``ed::place`` decides where each block runs.
* The kernels below are templated on a backend (``CpuBackend``, ``BasicCpuBackend<double>``
  for real blocks, or ``CudaBackend``).

:doc:`../architecture` describes how the layers fit together.

Conventions are the Python ones. A set bit is spin up (``ed::ops::kSetBitIsDown`` is false),
and ``Spec::n_up`` counts up spins (Sz = n_up - N/2).

Errors are the types of ``<ed/core/errors.h>``. The bindings translate them into
``qed.errors``.

Operators
---------

``Operator`` (``<ed/ops/operator.h>``, global namespace) is the operator the verbs take:

* records of one-, two- and three-body products of S+, S- and S^z;
* canonical extra terms on four or more sites;
* the full-space apply.

``Operator::canonical()`` is its ``ed::ops::MaskedOperator``: the unique sum of canonical
terms. It supports exact products, sums, adjoints and group images. ``ed::ops::to_operator``
writes a ``MaskedOperator`` back as an ``Operator``.

.. doxygenclass:: Operator

.. doxygenclass:: ed::ops::MaskedOperator

.. doxygenstruct:: ed::ops::MaskedTerm

``<ed/ops/invariance.h>``: the canonical terms of an ``Operator`` and the symmetry verdicts
on them, each relative to the largest coefficient.

.. doxygenfile:: ed/ops/invariance.h

``ed::LinearOperator`` is the one interface every solver consumes: a host ``apply`` and
``dim``, ``bind<Backend>()``, and ``bind_cuda()`` / ``bind_cuda_multi()`` for device lanes.

.. doxygenclass:: ed::LinearOperator

Placement
---------

``<ed/core/device.h>`` defines the device vocabulary:

* ``Device``: what the caller asks for;
* ``Lane``: where one block's solve runs, as counted in ``Placement``;
* ``Task``: what the block is solved for;
* ``auto_row``: the 'auto' table.

``<ed/core/select_backend.h>`` holds the one decision, ``ed::place``. It also provides
``ed::with_backend``, which runs a lane on its backend: the real host backend for a real
operator unless ``ED_SYM_REAL=0``, or the calling thread's ``CudaBackend``.

Backends
--------

The vector primitives the kernels run on. ``BasicBackend<Scalar>`` is the interface. The
host implementation is ``BasicCpuBackend<Scalar>`` (complex, or double for real blocks),
and the device implementation is ``BasicCudaBackend<Complex>`` (``<ed/gpu/cuda_backend.cuh>``,
CUDA builds only). ``MatvecBatcher`` runs independent samples in lockstep and serves their H
applies with one multi-vector apply.

Representative bases
--------------------

A symmetry sector is held as orbit representatives with their norms and the group action
(``RepSectorData``). For large groups, the representative is the orbit member that is least
in the key order of a block system of the group, where each block (sublattice) is a contiguous
range of key bits: ``SublatticeCode``. ``ED_SYM_SUBLATTICE`` chooses when: unset, for N >= 24
sites and at least 16 distinct site permutations under the relaxed rule (a verb on the device;
``eigs``, ``spectrum`` and exact ``thermal``) or 64 under the strict one (host sampled thermal and
host dynamics; ``SublatticeRuleScope``); ``1``, whenever a block system exists; ``0``, never. The orbits, norms and physics do not depend on it. A sector records the code it was
built with (``RepSectorData::slc``), and a saved result stores its fingerprint.
